# LNAudio 需求基线

> 状态：需求确认中  
> 本文记录已经明确的项目定位、技术选型和功能要求，并将尚未确认的事项单独列出。未确认的建议不得视为已定案的实现要求。

## 1. 项目定位

LNAudio 是一个面向 Windows 和 Android 的本地音乐播放器。

当前阶段只实现纯播放器功能，不开发多端同步能力。各设备独立管理本地音乐和播放状态，不依赖中心服务器、P2P 网络或其他设备。

## 2. 已确认要求

### 2.1 目标平台

- Windows
- Android

### 2.2 技术选型

| 范围 | 已确认方案 |
|---|---|
| 播放器核心 | C++ |
| 音频处理 | FFmpeg |
| Windows UI | Qt 6 Widgets |
| Android UI | Kotlin 原生 UI |

### 2.3 架构方向

- Windows 和 Android 共用 C++ 播放器核心。
- FFmpeg 用于音频媒体探测、解封装和解码；首期格式范围见第 2.6 节。
- Windows 使用 Qt 6 Widgets 构建桌面界面。
- Android 使用 Kotlin 构建原生界面。
- 两个平台的 UI 不直接承担音频解码工作，应通过播放器核心提供的接口操作播放功能。
- 平台相关的音频输出、设备管理和系统媒体控制应与共享播放逻辑分离。

### 2.4 音乐打开与播放方式

播放器必须同时支持以下两种使用方式：

1. **音乐库模式**：通过本地音乐库浏览和选择音乐进行播放。音乐库支持配置多个本地音乐目录，具体扫描和索引细节见第 2.5 节。
2. **直接播放模式**：用户通过平台文件选择器选择单个音乐文件后，可以立即播放，不要求先将文件导入音乐库。

两种模式共用同一套播放器核心和播放控制逻辑，不应分别实现独立的播放引擎。音乐库模式和直接播放模式产生的播放记录均纳入最近播放历史。

### 2.5 本地音乐目录

- 支持添加多个本地音乐目录作为音乐库来源。
- 播放器自动扫描已配置目录中的音乐文件，并将扫描结果纳入统一音乐库。
- 用户可以随时添加或移除已配置的音乐目录。
- Windows 与 Android 均提供对应平台的目录选择和访问授权流程。
- 对已配置目录自动监控文件系统变化，并提供手动刷新音乐库的操作。
- 检测到新增文件时，将符合音乐文件范围的文件加入音乐库；检测到删除、重命名或移动时，更新对应索引；文件内容发生变化时，重新读取相关媒体信息。
- 播放器启动时执行目录状态校验或增量扫描，用于补偿播放器未运行期间、监控机制未捕获或系统未上报的文件变化。
- 支持用户手动选择单个音乐文件或整个目录加入音乐库；手动加入的内容与自动扫描结果统一管理。
- 手动加入的文件或目录不要求必须位于已配置的自动扫描目录中。
- 同一音乐文件可以同时存在于不同目录；播放器不得因去重而删除、移动或修改用户的原始文件。
- 音乐库应识别重复音乐内容，避免将同一首音乐作为多个独立条目重复展示。
- 一个音乐库条目可以关联多个实际文件位置。
- 某个文件位置被删除或取消关联时，只移除该位置的关联；只要仍有其他有效位置，该音乐条目就继续保留。
- 具体监控 API、扫描调度和重复内容识别算法仍待确认。


### 2.6 首期音频格式

首期必须支持以下常见音频格式：

- MP3
- FLAC
- WAV
- AAC / M4A
- OGG / Opus
- WMA
- AIFF
- ALAC

由 FFmpeg 负责相应格式的媒体探测、解封装和解码。具体构建配置必须包含这些格式所需的解码器和解封装器；不能仅因使用 FFmpeg 就默认所有格式均已启用。


### 2.7 音乐库本地存储

- 使用 SQLite 作为本地音乐库数据库。
- 持久化音乐库条目、媒体元数据、文件位置及其关联关系。
- 持久化音乐目录配置及音乐库索引所需的状态。
- Windows 和 Android 各自使用本地数据库，互相独立，不进行跨设备同步。
- 数据库用于持久化索引和管理信息；音乐文件本身仍保留在用户原有位置，不复制进数据库。
- 数据库表结构、迁移策略以及播放列表的具体存储设计后续细化。

### 2.8 最近播放记录

- 保存用户最近播放过的音乐。
- 同时记录音乐库模式和直接播放模式的播放行为。
- 记录每首音乐的最后播放时间和累计播放次数。
- 提供最近播放列表供用户查看和再次播放。
- 提供清空播放历史的操作。

## 3. 当前明确不做的内容

当前阶段不包含：

- 多端播放状态同步
- 设备发现与设备配对
- P2P 通信
- 中心服务器或云端服务
- 跨设备音乐库同步
- 远程控制其他设备播放

未来是否增加上述能力，另行讨论；不得因此提前引入当前阶段不需要的网络或同步模块。

## 4. 候选功能范围

以下为播放器功能讨论清单，尚需逐项确认，不代表全部已经纳入首期：

- 本地音乐文件扫描与音乐库
- 音乐元数据读取
- 播放列表管理
- 播放、暂停、停止、上一首、下一首
- 播放进度显示与定位
- 音量控制
- 随机播放与循环播放
- 按歌曲、专辑、艺术家浏览
- 音乐搜索
- 专辑封面与歌词
- 均衡器
- 音频输出设备选择
- 后台播放与系统媒体控制

## 5. 待确认事项

### 5.1 音乐来源与音乐库

- 是否支持配置多个本地音乐目录并自动扫描。
- 是否支持手动将文件或目录加入音乐库。

- 音乐索引和播放列表采用何种本地存储方案。\n- 重复音乐内容的具体识别策略（文件哈希、音频指纹或组合策略）及其性能取舍。
- 直接播放的文件是否进入最近播放记录，以及是否提供最近播放列表。

### 5.2 音频能力

- 首期支持的音频格式及容器。
- Windows 音频输出后端。
- Android 音频输出后端。
- 是否需要无缝切歌、ReplayGain、均衡器及独占/低延迟输出。
- 采样率、位深和声道处理策略。

### 5.3 平台集成

- Android C++ 核心与 Kotlin UI 的 JNI 接口边界。
- Android 后台播放、前台服务、通知和 MediaSession 的具体要求。
- Windows 系统媒体按键、任务栏控制及快捷键要求。
- 两个平台的音频设备选择和音频焦点处理要求。

### 5.4 工程与依赖

- Qt 6 的具体版本。
- FFmpeg 的版本、构建方式、链接方式及许可证分发策略。
- Android NDK、SDK 和最低 Android 版本。
- Windows 最低支持版本及目标架构。
- 安装包、更新和发布方式。

## 6. 初步模块边界

以下是待进一步细化的逻辑边界，不是最终目录结构：

- **Player Core（C++）**：统一播放控制、播放状态和播放生命周期。
- **Media（C++ / FFmpeg）**：媒体探测、解封装、解码及音频数据处理。
- **Music Library（C++）**：本地文件索引、元数据和音乐库查询。
- **Playlist（C++）**：播放队列与播放列表逻辑。
- **Windows UI（Qt 6 Widgets）**：桌面交互和播放器状态展示。
- **Android UI（Kotlin）**：移动端交互和系统 UI 集成。
- **Platform Audio Output**：封装 Windows、Android 各自的音频输出实现。

模块是否需要独立成库，应在接口和依赖关系确认后再决定。

## 7. 需求确认原则

1. 先确认功能行为和模块边界，再建立工程结构并实现。
2. 已确认技术选型与候选建议必须明确区分。
3. 不为了未来可能的多端同步而提前增加网络协议或分布式架构。
4. 两个平台尽可能复用播放、媒体处理和音乐管理逻辑；平台 UI 与系统集成保持原生。
5. 本文随需求确认持续更新，并作为后续实现的需求依据。
